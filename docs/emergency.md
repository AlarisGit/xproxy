# Аварийный режим SSH

## Условия использования

При наличии `conf/tunnels.json` xproxy постоянно поддерживает один рабочий SSH-туннель и проверяет передачу данных через него. Поддержание туннеля не означает переключение клиентского трафика. Базовая проверка интернета не обращается к SSH-хостам.

| Ситуация | Действие |
|---|---|
| Active VLESS работает | Оставить трафик на нём, поддерживать VLESS standby и SSH |
| Active отказал, есть свежий рабочий VLESS standby | Переключить на standby |
| Active отказал, свежего рабочего standby нет, SSH готов | Переключить на SSH без ожидания обхода подписки |
| SSH отсутствует или заблокирован | Продолжать независимый поиск VLESS; использовать первый проверенный канал |
| Рабочий SSH, восстановился один VLESS | Оставаться на SSH |
| Рабочий SSH, два разных VLESS endpoint устойчивы 10 минут | Вернуть трафик на VLESS, второй оставить резервом, SSH сохранять |
| Текущий SSH подтверждённо отказал | Достаточно одного свежего VLESS, без десятиминутного ожидания; SSH восстанавливать параллельно |
| Все каналы недоступны | Искать VLESS двумя параллельными пробами, независимо повторять SSH; ускорить backoff |
| Резервный SSH работает | Сохранять его, основной профилактически не проверять |
| Нет интернета | Приостановить сетевые пробы и новые подключения; сохранять существующий SSH-процесс |

История пары VLESS хранится только в памяти и привязана к параметрам маршрута, fingerprint конфига и поколению сети. Разные UUID или названия стран одного endpoint не создают независимый резерв. Первый неудачный результат временно запрещает возврат и вызывает скорый повтор; подтверждённый отказ (два подряд либо три из пяти) сбрасывает историю кандидата. Успешный повтор после одиночного сбоя сохраняет историю, если между успешными наблюдениями прошло не больше 30 секунд. Смена параметров, устаревание наблюдений, сон/смена сети и перезапуск требуют новой стабилизации. Весь период должен перекрываться у обоих кандидатов.

## Локальная конфигурация

Создайте `conf/tunnels.json` по `conf/tunnels.template.json`. Шаблон содержит примерный адрес из документационного диапазона, который нужно заменить; он не предназначен для подключения. В git хранится только шаблон. У каждого клиента свой список.

```json
{
  "version": 1,
  "local_port": 20808,
  "tunnels": [
    {
      "id": "primary",
      "host": "203.0.113.10",
      "port": 22,
      "user": "xproxy",
      "identity_file": "~/.ssh/id_ed25519",
      "known_hosts_file": "~/.ssh/known_hosts",
      "remote_socks_port": 10808
    }
  ]
}
```

Порядок массива — приоритет. Следующий хост добавляется следующей записью. `id`, `host`, `user` обязательны; `id` уникален и используется в сводке. Необязательное поле `country` задаёт отображаемую страну (например, `"Франция"`); оно не влияет на подключение. По умолчанию SSH-порт 22, удалённый SOCKS 10808, локальный порт 20808. Локальный forward всегда слушает `127.0.0.1`; порты xray 10808/10809/10810 для него запрещены. Поддерживаются IP и DNS-имена; имена SSH разрешаются только при разрешённом подключении.

Пути к ключам/known_hosts абсолютные или начинаются с `~/`. `~` относится к пользователю xproxy. Если `identity_file` отсутствует, OpenSSH использует стандартные ключи/доступный агент. Для системного сервиса надёжнее явно указать ключ, доступный без интерактивного ввода. Без `known_hosts_file` требуется `~/.ssh/known_hosts`. Существование записи проверяется локально через `ssh-keygen -F`; отсутствие записи останавливает перебор. Для нестандартного порта запись имеет имя `[host]:port`.

Host keys нужно заранее получить и проверить по доверенному каналу администрирования. Автоматического `ssh-keyscan`, принятия неизвестных ключей или пробного обхода всех хостов в xproxy нет. Процесс использует `BatchMode=yes`, `StrictHostKeyChecking=yes` и `-F /dev/null`: пользовательские/system SSH config, ProxyJump, ProxyCommand, дополнительные forwards и multiplexing не подмешиваются. Нужные нестандартные параметры перенесите в поддерживаемые поля JSON.

На удалённой стороне SSH должен разрешать TCP forwarding к `127.0.0.1:<remote_socks_port>`, где работает xray SOCKS → freedom. Удалённый SOCKS не требуется открывать в интернет. Приватные ключи и адреса хостов не добавляйте в шаблон или git.

### Перечитывание

Файл проверяется в каждом основном цикле; задержка зависит от текущих проверок, обычно составляет один health-интервал. Ошибка JSON/схемы сохраняет последнюю разобранную конфигурацию, но запрещает **новые** SSH-подключения до исправления. Удаление файла или пустой массив также запрещают новые подключения.

Уже работающий аварийный туннель при отключении настройки продолжает обслуживать трафик до восстановления VLESS. Если он оборвётся, подключаться заново без разрешающего конфига нельзя. Подготовленный, но не используемый туннель при отключении закрывается. Изменение списка, приоритета, ключа или локального порта не заменяет здоровое действующее соединение: новые параметры применяются при следующем необходимом подключении. Сменившийся локальный порт публикуется в xray при необходимости восстановления трафика.

При обновлении ключа или `known_hosts_file` и прежних `id`, `host`, `port` текущий SSH сохраняет приоритет восстановления с новыми настройками, даже если он был резервным. Отмена попытки из-за потери сети или отключения настройки не считается отказом хоста и не переводит очередь на следующий адрес.

Чтобы избежать промежуточного невалидного JSON, сохраняйте файл через соседний временный файл и rename. Перезапуск xray или xproxy для перечитывания списка не нужен.

## Проверки и задержки

Базовые значения находятся в `xproxy/settings.py`:

| Проверка | Значение по умолчанию |
|---|---|
| Health active | через 5 с после итерации; после сбоя повтор через 1 с |
| Подтверждение отказа active | 2 подряд или 3 неудачи из последних 5 проб; наличие резерва порог не меняет |
| HTTPS через прокси | общий deadline 3 с на URL, включая DNS/SOCKS/TLS/тело; два IP-checker параллельно |
| VLESS standby при VLESS-трафике | повтор через 5 с; для переключения результат не старше 10 с |
| Пара VLESS при SSH-трафике | повтор каждого через 15 с; свежесть до 30 с |
| Неудачные VLESS | отдельные интервалы 1, 5, 15, 30, 60 с; при простое до 5 с |
| SSH ConnectTimeout | 10 с, одна попытка OpenSSH |
| Ожидание listener и e2e после запуска SSH | до 30 с |
| Проверка текущего SSH | каждые 10 с, READY действительно до 20 с |
| Подтверждение сбоя SSH supervisor | 2 неудачи; повтор через 3 с; завершившийся процесс считается потерянным |
| Повтор полного неудачного прохода SSH | 5, 15, 30, 60 с при рабочем VLESS; 1, 3, 5, 10, 15 с при простое |
| Добровольный возврат с SSH | два независимых VLESS с перекрывающимися 600 с устойчивых наблюдений |
| Возврат при отказавшем SSH | один свежий проверенный VLESS, без периода стабилизации |

В `.env` можно задать `XPROXY_VLESS_RECOVERY_SECONDS=600` (положительное число до 86400, требуется перезапуск). Некорректное значение заменяется значением по умолчанию.

Проверки используют получение полного ограниченного тела ответа, а не только открытие порта/HTTP-заголовки. Для проверки upstream новый production-конфиг содержит локальный SOCKS `127.0.0.1:10810` с принудительным маршрутом в outbound `proxy`. Старый конфиг до первой проверенной пересборки проверяется через клиентский порт. Временные xray используют свободные порты и не занимают production listener.

При подготовке возврата с исправного SSH каждый VLESS также периодически, примерно раз в минуту, скачивает 256 КиБ через принудительный upstream с общим пределом 10 с. Источник по умолчанию — [Cloudflare Speedtest](https://github.com/cloudflare/speedtest), `https://speed.cloudflare.com/__down?bytes=262144`. В `.env` его можно заменить через `XPROXY_STREAM_CHECK_URL`; HTTPS URL должен возвращать ровно 262144 байта без редиректов. Отказ этой пробы запрещает добровольный возврат, но не исключает канал из экстренного восстановления: отказ одного контрольного сайта не доказывает блокировку всего маршрута. Такая проба не гарантирует сохранность любого длительного пользовательского соединения.

HTTP-пробы прокси выполняются в короткоживущих дочерних процессах Python: по общему deadline процесс завершается и забирается, поэтому медленно поступающее тело или зависший DNS не оставляют вечную пробу. Проверки VLESS выполняются максимум в двух временных xray; успешный результат публикуется без ожидания второй задачи. Переключение по-прежнему требует проверки конфига, restart xray и проверки production-трафика, поэтому интервалы не являются гарантией времени восстановления и текущие клиентские соединения могут оборваться.

Локальная неисправность xray, занятый порт, отсутствующий ключ/known_hosts или невозможность запуска SSH дают локальную ошибку и backoff. Ошибка аутентификации/host key после соединения считается отказом данного SSH-хоста; подробности остаются в `state/ssh.log`. VLESS-пробы и восстановление SSH не ждут друг друга. Изменение приоритета не заменяет работающий канал.

Если настроен `sync.json`, переход на другой VLESS после аварии запускает публикацию его проверенного конфига для внешних клиентов сразу после фиксации перехода, независимо от постоянно поддерживаемого SSH. Возврат на прежний VLESS без изменения параметров не публикуется повторно. Ни вход в аварийный режим, ни смена SSH-хоста не публикуют локальный SOCKS-конфиг.

## Сон, перезапуск, миграция

Наличие базового интернета проверяется независимо от прокси: ping публичных IP, затем, если ICMP не дал ответа, прямые HTTPS-запросы к нескольким сайтам. Достаточно одного успешного ping или получения HTTP-ответа по проверенному TLS; внешний IP и доступность Telegram здесь не требуются. Основной цикл и дополнительные перепроверки аварийного контроллера используют одинаковую функцию. Список адресов и таймауты — `INTERNET_PING_*` / `INTERNET_HTTP_*` в `settings.py`, подробности — в [архитектуре](architecture.md).

Транспорт определяется по реальному `proxy` outbound в конфиге xray. Сохранённый `active.json` — последний VLESS, а не доказательство, что трафик сейчас идёт через него. После запуска старые READY не считаются достоверными. Настроенный SSH восстанавливается при наличии сети, независимо от результатов VLESS.

Управляемый SSH записывается в `state/ssh-process.json`: PID, время создания/команда и уникальный маркер. После exec/crash supervisor может принять совпадающий локальный процесс; посторонние `ssh -L` он не завершает. Если systemd/launchd уже завершил дочерний процесс, supervisor восстанавливает настроенный туннель после подтверждения сети. При подтверждённом offline работающий процесс сохраняется; новых проверок и переподключений нет. Уже установленный SSH может отправлять собственные keepalive — приостановка supervisor не является сетевым firewall.

Состояние сети действительно 90 секунд по монотонным и календарным часам. Если оно истекло хотя бы по одним часам, следующая проверка создаёт новое поколение и сбрасывает старые standby/отказы, даже при прежнем default route. Это учитывает сон macOS, во время которого монотонные часы могут почти не продвинуться.

Ручные `start-fr-tunnel.sh` и `stop-fr-tunnel.sh` удалены. Для перехода с прежнего режима:

1. Подготовьте локальный `tunnels.json` с тем же host/user/SSH-port/remote SOCKS и локальным портом старого forward. Согласуйте ключи с явной конфигурацией OpenSSH выше.
2. Запустите новую версию xproxy как сервис. Старый режим останавливал xproxy, поэтому одного обновления файлов для запуска supervision недостаточно.
3. При старте supervisor ищет только одноимённый старый цикл `~/.fr-tunnel/ssh-tunnel-fr.sh` текущего пользователя и его SSH-потомка с точным совпадением endpoint/портов. Он сохраняет владение, завершает старый цикл и принимает существующий SSH без нового handshake. Если цикл находится в `sleep 30` после ошибки, supervisor проверяет содержимое старого сгенерированного скрипта и совпадение настроек, затем завершает цикл без нового подключения.
4. Если процесс нельзя однозначно сопоставить или он запущен другим способом, xproxy его не убивает: занятый порт диагностируется как локальная ошибка. Остановите такой цикл адресно средствами его запуска; не используйте широкий `pkill ssh`.

Старый marker `~/.fr-tunnel/emergency.active` не управляет новой логикой. Старые файлы/бэкапы в домашнем каталоге автоматически не удаляются. Возврат на VLESS строится из актуальных настроек и проверенного кандидата, а не копированием старого аварийного бэкапа.

## Ограничения TCP

SSH `-L` переносит TCP. SOCKS UDP и QUIC через этот forward не работают. Emergency builder сохраняет клиентские inbounds, production logging и правила direct/proxy/block; UDP/QUIC DNS переводит на DoH при заданном DNSDomain, иначе на DNS-over-TCP. Произвольный UDP-трафик автоматически не преобразуется в TCP. Когда приложение поддерживает TCP fallback, оно может продолжить работу; для UDP-only приложений этот аварийный режим недостаточен.
