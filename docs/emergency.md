# Аварийный режим SSH

## Условия использования

SSH-хосты не участвуют в обычной проверке доступности интернета и подборе VLESS. Чтение `tunnels.json`, проверка файлов ключей и поиск записи в локальном `known_hosts` не обращаются к удалённому хосту.

| Ситуация | Действие |
|---|---|
| VLESS active работает, standby проверен | SSH не запускается и не проверяется |
| Standby ещё не проверен после старта | Продолжается поиск VLESS, SSH не запускается только из-за пустого слота |
| Active работает, все доступные альтернативы действительно провалили проверки | Подготовить первый SSH; трафик остаётся на VLESS |
| Active подтверждённо не работает, готового standby нет | Разрешить подготовку SSH; полный проход VLESS не задерживает спасение трафика |
| SSH готов и active VLESS отказал | Проверить и применить конфиг с локальным SOCKS-концом туннеля |
| Текущий SSH перестал передавать трафик | Подтвердить сбой и интернет; восстановить этот же хост, затем пробовать остальные по приоритету |
| Резервный SSH работает | Продолжать использовать его; основной SSH профилактически не проверять |
| VLESS восстановился | Проверить повторно и переключить трафик; удерживать существующий SSH до стабилизации |
| VLESS стабилен и есть свежий независимый standby | Завершить туннель и прекратить SSH-проверки |
| Нет интернета | Ждать восстановления сети; не перебирать адреса и не начислять штрафы |

Пустая подписка, отсутствие разрешённых альтернатив и ошибки локальной конфигурации не являются доказательством массовой блокировки. Отрицательные результаты VLESS действуют 5 минут. Для длинного списка учитывается также полностью неудачный непрерывный проход, завершённый не более 5 минут назад. Найденный рабочий standby завершает проход: его последующая потеря требует нового поиска, а не повторного использования старого списка отказов. Смена сети, рестарт и инвалидирование входных данных сбрасывают доказательства.

## Локальная конфигурация

Создайте `conf/tunnels.json` по `conf/tunnels.template.json`. Шаблон содержит примерный адрес из документационного диапазона, который нужно заменить; он не предназначен для подключения. В git хранится только шаблон. У каждого клиента свой список.

```json
{
  "version": 1,
  "local_port": 20808,
  "tunnels": [
    {
      "id": "primary",
      "host": "203.0.113.10",
      "port": 22,
      "user": "xproxy",
      "identity_file": "~/.ssh/id_ed25519",
      "known_hosts_file": "~/.ssh/known_hosts",
      "remote_socks_port": 10808
    }
  ]
}
```

Порядок массива — приоритет. Следующий хост добавляется следующей записью. `id`, `host`, `user` обязательны; `id` уникален и используется в уведомлениях. По умолчанию SSH-порт 22, удалённый SOCKS 10808, локальный порт 20808. Локальный forward всегда слушает `127.0.0.1`; клиентские порты 10808/10809 для него запрещены. Поддерживаются IP и DNS-имена; имена SSH разрешаются только при разрешённом подключении.

Пути к ключам/known_hosts абсолютные или начинаются с `~/`. `~` относится к пользователю xproxy. Если `identity_file` отсутствует, OpenSSH использует стандартные ключи/доступный агент. Для системного сервиса надёжнее явно указать ключ, доступный без интерактивного ввода. Без `known_hosts_file` требуется `~/.ssh/known_hosts`. Существование записи проверяется локально через `ssh-keygen -F`; отсутствие записи останавливает перебор. Для нестандартного порта запись имеет имя `[host]:port`.

Host keys нужно заранее получить и проверить по доверенному каналу администрирования. Автоматического `ssh-keyscan`, принятия неизвестных ключей или пробного обхода всех хостов в xproxy нет. Процесс использует `BatchMode=yes`, `StrictHostKeyChecking=yes` и `-F /dev/null`: пользовательские/system SSH config, ProxyJump, ProxyCommand, дополнительные forwards и multiplexing не подмешиваются. Нужные нестандартные параметры перенесите в поддерживаемые поля JSON.

На удалённой стороне SSH должен разрешать TCP forwarding к `127.0.0.1:<remote_socks_port>`, где работает xray SOCKS → freedom. Удалённый SOCKS не требуется открывать в интернет. Приватные ключи и адреса хостов не добавляйте в шаблон или git.

### Перечитывание

Файл проверяется в каждом основном цикле; задержка зависит от текущих проверок, обычно составляет один health-интервал. Ошибка JSON/схемы сохраняет последнюю разобранную конфигурацию, но запрещает **новые** SSH-подключения до исправления. Удаление файла или пустой массив также запрещают новые подключения.

Уже работающий аварийный туннель при отключении настройки продолжает обслуживать трафик до восстановления VLESS. Если он оборвётся, подключаться заново без разрешающего конфига нельзя. Подготовленный, но не используемый туннель при отключении закрывается. Изменение списка, приоритета, ключа или локального порта не заменяет здоровое действующее соединение: новые параметры применяются при следующем необходимом подключении. Сменившийся локальный порт публикуется в xray при необходимости восстановления трафика.

При обновлении ключа или `known_hosts_file` и прежних `id`, `host`, `port` текущий SSH сохраняет приоритет восстановления с новыми настройками, даже если он был резервным. Отмена попытки из-за потери сети или исчезновения аварийной потребности не считается отказом хоста и не переводит очередь на следующий адрес.

Чтобы избежать промежуточного невалидного JSON, сохраняйте файл через соседний временный файл и rename. Перезапуск xray или xproxy для перечитывания списка не нужен.

## Проверки и задержки

Значения находятся в `xproxy/settings.py`:

| Проверка | Значение по умолчанию |
|---|---|
| Основной health-интервал | 15 с после завершения итерации |
| Отказ active без готового резерва | 5 последовательных неудач |
| Отказ active с готовым VLESS/SSH резервом | 1 неудача |
| SSH ConnectTimeout | 10 с, одна попытка OpenSSH |
| Ожидание listener и e2e после запуска SSH | до 30 с после запуска процесса |
| Проверка текущего SSH | каждые 30 с |
| Подтверждение сбоя текущего SSH | 2 неудачи; повтор через 3 с; завершившийся SSH-процесс сразу считается потерянным |
| Полностью неудачный проход SSH | паузы 30, 60, 120, 300 с |
| Восстановление VLESS при рабочем SSH | 2 успешные подготовки одного кандидата с интервалом не менее 15 с |
| Возврат, когда текущий аварийный канал уже не работает | достаточно одного проверенного VLESS-кандидата |
| Закрытие удерживаемого SSH | 120 с стабильных наблюдений active и наличие standby с проверкой не старше 30 с |

Это интервалы планирования, а не гарантия общего времени восстановления: DNS, HTTP-пробы, локальная валидация и перезапуск сервиса требуют дополнительного времени. У SSH есть keepalive 30 с × 3. Проверка трафика идёт через SOCKS к IP-checker и целевым ресурсам; открытого TCP-порта недостаточно.

При обнаружении ошибки сначала повторно подтверждается интернет. Локальная неисправность xray, занятый порт, отсутствующий ключ/known_hosts или невозможность запуска SSH останавливают попытки с backoff, не раскрывая следующие адреса. Ошибка аутентификации/host key, обнаруженная самим SSH после соединения, считается неудачей этого хоста; подробности остаются в локальном `state/ssh.log`.

Во время удержания SSH после возврата на VLESS проверяется только существующее соединение. Новый handshake в этот период разрешается лишь при новой подтверждённой проблеме VLESS. Стабилизация прерывается при неуспешной/устаревшей проверке, смене активного маршрута или сети.

Если настроен `sync.json`, переход на другой VLESS после аварии запускает публикацию его проверенного конфига для внешних клиентов сразу после фиксации перехода, без ожидания закрытия удерживаемого SSH. Возврат на прежний VLESS без изменения параметров не публикуется повторно. Ни вход в аварийный режим, ни смена SSH-хоста не публикуют локальный SOCKS-конфиг.

## Сон, перезапуск, миграция

Транспорт определяется по реальному `proxy` outbound в конфиге xray. Сохранённый `active.json` — последний VLESS, а не доказательство, что трафик сейчас идёт через него. После запуска старые READY/ошибки не используются для раскрытия SSH-адресов. Даже если на диске SSH-конфиг, новое подключение требует свежего отказа VLESS.

Управляемый SSH записывается в `state/ssh-process.json`: PID, время создания/команда и уникальный маркер. После exec/crash supervisor может принять совпадающий локальный процесс; посторонние `ssh -L` он не завершает. Если systemd/launchd уже завершил дочерний процесс, требуется обычное восстановление по свежим условиям. При подтверждённом offline работающий процесс сохраняется; новых проверок и переподключений нет. Уже установленный SSH может отправлять собственные keepalive — приостановка supervisor не является сетевым firewall.

Состояние сети действительно 90 секунд по монотонным и календарным часам. Если оно истекло хотя бы по одним часам, следующая проверка создаёт новое поколение и сбрасывает старые standby/отказы, даже при прежнем default route. Это учитывает сон macOS, во время которого монотонные часы могут почти не продвинуться.

Ручные `start-fr-tunnel.sh` и `stop-fr-tunnel.sh` удалены. Для перехода с прежнего режима:

1. Подготовьте локальный `tunnels.json` с тем же host/user/SSH-port/remote SOCKS и локальным портом старого forward. Согласуйте ключи с явной конфигурацией OpenSSH выше.
2. Запустите новую версию xproxy как сервис. Старый режим останавливал xproxy, поэтому одного обновления файлов для запуска supervision недостаточно.
3. При старте supervisor ищет только одноимённый старый цикл `~/.fr-tunnel/ssh-tunnel-fr.sh` текущего пользователя и его SSH-потомка с точным совпадением endpoint/портов. Он сохраняет владение, завершает старый цикл и принимает существующий SSH без нового handshake. Если цикл находится в `sleep 30` после ошибки, supervisor проверяет содержимое старого сгенерированного скрипта и совпадение настроек, затем завершает цикл без нового подключения.
4. Если процесс нельзя однозначно сопоставить или он запущен другим способом, xproxy его не убивает: занятый порт диагностируется как локальная ошибка. Остановите такой цикл адресно средствами его запуска; не используйте широкий `pkill ssh`.

Старый marker `~/.fr-tunnel/emergency.active` не управляет новой логикой. Старые файлы/бэкапы в домашнем каталоге автоматически не удаляются. Возврат на VLESS строится из актуальных настроек и проверенного кандидата, а не копированием старого аварийного бэкапа.

## Ограничения TCP

SSH `-L` переносит TCP. SOCKS UDP и QUIC через этот forward не работают. Emergency builder сохраняет клиентские inbounds, production logging и правила direct/proxy/block; UDP/QUIC DNS переводит на DoH при заданном DNSDomain, иначе на DNS-over-TCP. Произвольный UDP-трафик автоматически не преобразуется в TCP. Когда приложение поддерживает TCP fallback, оно может продолжить работу; для UDP-only приложений этот аварийный режим недостаточен.
