# Telegram: события и доставка

Настройка прежняя: оба ключа `TELEGRAM_BOT_TOKEN` и `TELEGRAM_ALERTS_USER_ID` в локальном `.env`. Без них xproxy работает автономно, события остаются в логах.

## Модель событий

Уведомление представляет состояние отдельной темы. Новое событие заменяет ещё не отправленное событие **той же темы**. Это позволяет после восстановления интернета получить актуальные сведения вместо очереди устаревших «упал/поднялся». Полная история переходов остаётся в локальном логе.

| Тема | Содержание | Когда отправляется |
|---|---|---|
| `routes` | Active/standby, endpoint, транспорт | После 3 одинаковых наблюдений с интервалом не менее 30 с |
| `tunnel` | SSH READY, FAILED, LOCAL_ERROR, SUSPENDED, IDLE; `id` хоста | При подтверждённом изменении |
| `transport` | Вход в SSH, возврат на VLESS с удержанием SSH, завершение аварийного эпизода | Сразу в очередь после успешного перехода |
| `network` | Пропадание/восстановление интернета | При смене подтверждённого состояния |
| `configuration` | Ошибка/исправление/отключение `tunnels.json` | При изменении локальной настройки |
| `config` | Ошибка локального xray, неуспешная смена/rollback | При существенном сбое |
| `subscription`, `geo`, `sync`, `update` | Результаты соответствующей фоновой операции | Ошибки и значимые изменения |
| `lifecycle`, `heartbeat` | Старт/остановка, суточный статус | На событие/раз в сутки |

`routes` различает смену endpoint даже внутри одной страны и отражает SSH вместо имени старого VLESS. Первый здоровый статус после старта задаёт baseline; первый устойчиво неработающий active уведомляется. Во время offline серия наблюдений сбрасывается.

Промежуточные стадии VLESS `PREPARING/PROMOTING/EMPTY`, SSH `CONNECTING/CHECKING`, каждое обновление TTL и повторные одинаковые статусы не создают отдельных Telegram-сообщений. Отказ рабочего туннеля подтверждается перед оповещением и перебором. Успех запасного SSH отображается с его `id`; адреса, ключи и подробности команды остаются локальными.

## Доставка

- Фоновый sender использует общий кэш состояния сети. Offline не расходует попытки доставки и не вызывает новых SSH-подключений.
- Маршрут отправки: существующий SOCKS xray → direct. После удачи второй маршрут не используется. Telegram-ошибка никогда не запускает SSH сама по себе.
- Очередь сохраняется в `state/notify_queue.json` и восстанавливается до добавления первого события, даже если ошибка конфигурации обнаружена раньше запуска sender. Загрузка и объединение сериализованы с добавлением событий; новое состояние заменяет только свою тему. Максимум 256 событий, срок жизни 24 часа, максимум 10 попыток отправки с экспоненциальной паузой до 30 минут.
- Для сообщений без темы сохранён throttle одинакового текста 60 с. Для состояний темы он не мешает цепочке READY→FAILED→READY; одинаковые состояния подавляются источником события.
- Время в `[HH:MM:SS]` — время события, а не отложенной доставки. Префикс содержит hostname и, если удалось определить, direct public IP из кэша; суффикс показывает текущее состояние процесса/маршрутов.
- События с темой всегда проходят очередь, включая вызовы с `blocking=True`; перед shutdown/exec выполняется короткий drain, остаток остаётся на диске.

Если сообщение уже ушло в HTTP-запрос до появления нового состояния, отменить доставку нельзя. Завершение старой отправки не удаляет более новое событие из очереди. При неоднозначном сетевом ответе Telegram возможен повтор: API sendMessage не даёт строгой гарантии exactly-once. Недоступность интернета/Telegram также означает, что мгновенную доставку гарантировать нельзя.
